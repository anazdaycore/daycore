# PWA 与家庭模式：计划书（未开工）

> **状态：计划书。** 2026-09-18 应所有者要求先出方案 —— 本文档**不含任何代码改动**。
> 每节标了「建议」（可以先按这个做）与「待拍板」（不拍不动）。
> 关联：[`ROADMAP.md`](ROADMAP.md)（阶段 κ 之后）、[`ARCHITECTURE.md`](ARCHITECTURE.md)（每会话时区、通道、降级启动）、`internal/notify`（推送的现成接缝）。

## 0. 为什么这两件事写在一份里

PWA 不是「让网页能装」这一件事。它同时给出家庭模式缺一不可的三样东西：

1. **安装**（standalone 外壳）—— 家人之间互相提醒，需要它先像一个 app；
2. **离线** —— 地铁上、飞机上也能看今天的安排；
3. **推送** ——「到家了」「作业要交了」这类联动必须在 app 不在前台时也能到达。

反过来，家庭模式是 PWA 之后最值得做的一件事：它把单用户工具变成有理由互相拉新的产品面。所以顺序是硬的：**PWA（可安装 + 推送）→ 家庭联动**。反过来做，联动只能退化成前台轮询。

⚠️ 但这两块都**不是现在**。本文只出文档。

## 1. 前端 PWA

### 1.1 现状（逐条可查）

- 四个前端是独立 git 子仓库，Vite 6 + React 18，`base: './'`（相对资源路径，见 `web/liuli-classic/vite.config.ts` 里那段理由），各自 `npm run build` → `dist/`，静态托管在 nginx 子路径（生产：`/ting/`、`/zhiyu/`、`/liuli/`、`/liuli-classic/`）。
- **没有任何 PWA 产物**：`web/liuli-classic/public/` 下只有 `locales/`，无 manifest、无 service worker、无图标；`index.html` 里没有 `manifest` 链接。
- **后端没有 Web Push**：`internal/notify` 是已经设计好的投递总线（注册表 + driver 自注册，文件头明确把 Web Push / APNs / FCM / 通道外发都列为合法 driver），但今天**一个 driver 都没注册**，事实轨通知因此退化成「通道」（目前多半是 OneBot）。
- HTTPS 已经是生产现状，这是 PWA 的硬前提之一，不用额外解决。

### 1.2 要新增什么（每端 3 个文件 + 1 行注册）

| 产物 | 放哪 | 关键约束 |
|---|---|---|
| `manifest.webmanifest` | 各端 `public/` | ⚠️ `start_url` / `scope` 用**相对**（`./`），与 `base: './'` 同一个理由：这个构建不知道自己的 URL，写死 `/` 会让子路径部署安装出一个打不开的壳 |
| `sw.js` | 各端 `public/`（**不**进 hash） | 更新策略见 1.4；`skipWaiting` 必须可控，否则用户永远拿旧壳 |
| 图标 | 各端 `public/icons/` | 192 / 512 + `maskable`（Android 自适应）+ `apple-touch-icon`（iOS 不吃 manifest 里的图标） |
| 注册 | 各端 `main.tsx` 一行，逻辑放 `packages/core` | 四端共用一份，避免四份不一致 |

### 1.3 iOS 与 Android 的差异（按更严的 Apple 设计）

| | Android / Chrome | iOS / Safari |
|---|---|---|
| 安装入口 | `beforeinstallprompt`，可以自己弹 | **没有**这个事件，只能引导「分享 → 添加到主屏幕」 |
| 推送 | Web Push（VAPID） | **16.4+ 且必须先安装到主屏幕**；底层走 APNs 桥，协议仍是 Web Push |
| manifest | 完整支持 | 只吃一部分：`display`、`theme_color`，图标要 `apple-touch-icon` |
| 后台限制 | 宽松 | SW 回收积极，离线队列必须在**前台**也尝试冲刷 |

结论（建议）：**不依赖 `beforeinstallprompt`**。安装引导做成一屏图文，iOS / Android 两套说明 —— 否则 iOS 用户永远装不上，而那是家长端最该覆盖的平台。

### 1.4 更新与离线的边界（这一节是踩坑清单，不是功能清单）

- **缓存策略**：壳（HTML / JS / CSS）走 stale-while-revalidate；`/api/*` **永不缓存** —— 陪伴的答案不能来自缓存。
- **离线只做三件**：看今日计划（最近一次成功响应）、心情打卡（入队）、划掉简报（入队）。其余一律明说「需要联网」，不要假装成功。
- ⚠️ **离线写与 append-only 操作日志的关系**：写操作是「服务端执行 + 记 op 日志」，重放必须幂等。每条入队的写带一个客户端生成的 `opId`，服务端按 `(sid, opId)` 去重 —— 否则一次网络重试会让同一笔心情记两遍。**这个 `opId` 面今天不存在**，它是离线写的前置条件，不是顺带能加的东西。
- ⚠️ **多端并发**：同一会话在两台设备（家里平板 + 手机）各离线改一笔，回来后需要 LWW 或冲突提示。今天的 `rev` CAS 已经能拒绝陈旧写，前端要**把 409 给用户看**，而不是静默重试。

### 1.5 推送（服务端）

- 用现成的接缝：在 `internal/notify` 加一个 `webpush` driver（VAPID），订阅表 `push_subscriptions(session_id, endpoint, p256dh, auth, ua, created_at, last_seen_at, failures)`。
- 谁能收到什么必须过现有闸：`SessionPrefs.doNotDisturb`（夜间不打扰）、以及 `notify` 文件头那条 —— **建议永不走这条总线**，推送正是这条总线。
- 与 cron 简报的关系：简报仍然落库（App 读得到），推送只是「把它送到」的最后一步；**不能**变成「只有推送成功才算发过」。

### 1.6 四端共用还是各写一份

建议：SW / manifest 的**逻辑**放 `packages/core`（或新的 `packages/pwa`），图标与 `manifest.webmanifest` 每端一份（名字、主题色、图标不同）。理由：逻辑共用、品牌各异，而四端是四个子仓库，共用代码本来就有发布通道（κ 那套 pin）。

**待拍板**：是否接受「改一次 PWA 逻辑 = 发一次 core + 四端各 bump」这个成本。

### 1.7 验收探针（缺一条都不算做完）

1. Android Chrome：可安装，安装后 standalone 打开不是浏览器壳；
2. iOS Safari 16.4+：添加到主屏幕后能收到**一条真实推送**（不是本地通知）；
3. 断网：打开 app 能看到今日计划，打卡入队，恢复网络后**只写一次**；
4. 发新版：用户刷新后拿到新壳（证明 SW 更新路径没有死锁）。

## 2. 家庭模式（参考 Apple「查找」与小米「查找」）

### 2.1 两家的机制拆解（只拆机制，不抄界面）

| 机制 | Apple 家人共享 / 查找 | 小米查找 | daycore 的对应物 |
|---|---|---|---|
| 组 | 家人共享，人数有上限 | 家庭组 | `Family`（规模上限待拍板） |
| 角色 | 组织者 / 成人 / 儿童（儿童由家长代持同意） | 管理员 / 成员 | `owner` / `adult` / `child` |
| 邀请 | 面对面、链接、邀请码 | 邀请码 | 邀请码 + 有效期 |
| 共享什么 | 位置（人、设备）、到达离开通知 | 位置、设备 | **安排与存在**，不是位置轨迹（见 2.4） |
| 谁能看谁 | 双向可见；儿童对家长单向 | 管理员可见成员 | 默认双向；儿童对家长单向 + 审计 |
| 通知 | 到达 / 离开某地 | 到达 / 离开、低电量 | 「到家了」「该睡了」「作业要交了」 |
| 退出 | 随时退出，组织者可移除 | 同 | 同 + 数据归属要显式说明 |

一句话：两家的核心是**一个受角色约束的共享面 + 事件通知**，不是地图。我们要的是前一半。

### 2.2 我们共享的是什么（产品判断，不是技术选择）

- ✅ 共享：今日 / 明日的**安排骨架**（哪个时段有没有空）、截止日、**状态信号**（到家 / 睡了 / 在忙）。
- ⚠️ **心情默认不共享。** 陪伴产品的全部价值建立在「这里没有评分」上；心情一旦对家人可见，它就变成绩效。将来若要做，必须是**逐次显式分享**（这一次打卡，分享给家人），且家人看不到趋势与 valence。
- ❌ 不共享：位置轨迹、消息内容、AI 对话内容、记忆片段。

### 2.3 联动清单（「可以让用户联动」，按价值排序）

1. **家庭日程冲突**：给家人排共享块时，若与对方已有块冲突，当场提示（「妈妈 19:00 也在接你」）。
2. **共享块**：接送、家务、家庭活动作为 `visibility: family` 的时间块，家人能看到、能认领。
3. **到家 / 平安打卡**：一键，家人收到通知。这是 PWA 推送的第一个真实用例。
4. **家庭周信**：把现有周信扩成「这一周家里发生了什么」，逐人选择加入，默认只有自己。
5. **缺席问候**：家人连续两天没有安排或打卡时，问一句「要不要帮他」—— ⚠️ **不**自动告知家人。

### 2.4 伦理与边界（最重要的一节，改这块代码的人先读这里）

- **不做监控。** 不做位置追踪，不做「看家人在干什么」的实时面，不做静默上报。
- **可见性默认最小**：加入家庭组不改变任何既有块的可见性；共享是逐项选择的结果。
- **儿童账号**：家长代持同意 + **孩子能看到「谁在什么时候看了什么」**（审计面同时给孩子）。这条是产品底线，不是合规装饰。
- **退出即断开**：退出后家人看不到任何新数据；历史共享块保留与否要显式问一次。
- **措辞**：全产品不许出现「监督 / 管理 / 管控」类词，只许「约定 / 一起 / 提醒」。

### 2.5 数据模型草案（供评审）

- `families(id, name, owner_session_id, created_at)`
- `family_members(family_id, session_id, role, alias, joined_at, state)` —— role: owner|adult|child；state: active|left|removed
- `family_invites(code, family_id, role, expires_at, created_by, used_by)`
- 共享面：`time_blocks.visibility`（private|family）—— ⚠️ 这是**加列**，要走 `ColumnMigration`，三方言 DDL 与 mongostore doc struct 同批改（本仓铁律，`dialect_parity_test.go` 会盯）
- `family_events(id, family_id, actor_session_id, kind, payload, created_at)` —— 到家 / 平安 / 认领
- `push_subscriptions(...)`（见 1.5）
- `family_audit(viewer_session_id, subject_session_id, scope, at)` —— 2.4 的审计面

### 2.6 API 面草案（tag: `family`）

`POST /api/v2/family`（建组）、`POST /api/v2/family/invite`、`POST /api/v2/family/join`、`GET /api/v2/family`（成员 + 我的共享面）、`PATCH /api/v2/family/members/{sid}`（角色 / 移除）、`DELETE /api/v2/family/leave`、`GET /api/v2/family/audit`、`PATCH /api/v2/family/blocks/{id}/visibility`。

权限矩阵（草稿）：`owner` 可改成员；`adult` 只能管自己与孩子；`child` 只能看自己的共享面与审计；任何跨会话读都必须过 `family_members` 且被读者在自己的共享面内。

⚠️ 这一层必须复用本仓既有的鉴权惯例（`requireSession` + 显式授权 + `auth_surface_test.go` 的端点名单），**不要**新造一套。

### 2.7 分期与出口标准

- **F1 家庭组与成员**：建组 / 邀请 / 加入 / 退出 / 角色 + 审计面。探针：两个会话互相加入后各自看到成员；非成员一律 403。
- **F2 共享日程**：`visibility` + 家人只读视图 + 冲突提示。探针：A 的 private 块对 B 不可见；family 块可见且冲突被提示。
- **F3 到家 / 平安联动 + 推送**：依赖第一部分。探针：A 打卡到家，B 的设备收到一条推送。
- **F4 家庭周信与缺席问候**：文案与频率要再过一遍陪伴边界。

### 2.8 待所有者拍板（不拍不动）

1. 家庭规模上限（Apple 是 6）—— 按 6，还是「不限人数但推送限速」？
2. 儿童账号的年龄门槛与「家长代持」的具体流程？
3. 一个人能不能同时在两个家庭组（两地 / 离异家庭是真实场景）？
4. 到家打卡是手动一键，还是允许地理围栏自动？后者要位置权限，与 2.4 直接冲突 —— **建议手动**。
5. 共享块的默认可见性（**建议 private**，逐块选择）？
6. 是否接受「iOS 必须先安装到主屏幕才有推送」这个接受度代价？

## 3. 顺序与依赖（硬依赖，不可调）

1. PWA 壳与离线（无依赖）
2. `opId` 幂等面（离线写的**前置**）
3. `internal/notify` 的 `webpush` driver + 订阅表（依赖 1 的 SW）
4. F1 家庭组（可与 3 并行）
5. F2 共享日程 → F3 联动推送（依赖 3 + 4）
6. F4 文案与频率（依赖 F3 的真实使用数据）

## 4. 明确不做（写在这里，免得被当成疏漏「顺手加上」）

- 不做位置实时共享 / 地理围栏追踪（除所有者另行拍板）
- 不做心情趋势的家庭可见
- 不做家庭内聊天（我们已经有陪伴对话，不再造一个 IM）
- 不做家长静默查看孩子的 AI 对话
- 不做广告、推荐位
- PWA 不为 SEO 或分享卡做文章：这是 app，不是落地页
